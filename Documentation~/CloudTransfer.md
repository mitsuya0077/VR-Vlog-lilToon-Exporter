# 開発用：QRコードでスマホに送る

この文書はGitに残す開発用の仕様・検証手順です。QR転送は未公開で、QR転送対応版の配布バージョンは未定です。次の配布候補 **0.11.11-beta.17** は **VRM書き出し専用版** とし、このガイドとQR転送実装を配布パッケージに含めません。E2E暗号化の実装は開発用ソースに保持します。

現在のソースでも転送ボタンと起動経路を外し、復元された転送画面からも開始できないようにしています。以下の操作は、将来UIを再接続して機能を有効化した開発環境で行う受入手順です。現在は合成データとfake transportによるホスト試験でE2E実装を検証します。実際の転送には転送サービスとQR v3対応のAndroid・iPhone版VR Vlogの準備が必要です。以前のLAN QR、暗号化前のQR v2、通常のカメラアプリでは受け取れません。

## 接続条件と一時保存

PCとスマホの両方にインターネット接続が必要です。同じWi-FiやLAN接続、PCのポート開放は不要です。完成済みVRMをPCで暗号化し、通常のHTTPSで固定のVR Vlog転送サービスへアップロードします。復号鍵はQRにだけ含め、サービスには送りません。元のファイル名や元のVRMのハッシュもサービスには送らず、暗号化したファイルだけを一時保存します。VRMは転送のために再変換せず、スマホで認証・復号した後もlilToon、表情、ライセンス情報を含む完成済みファイルのバイト列を維持します。

アバターはクラウドへ一時保存されます。受取期限は転送作成時から **3分**、容量上限は **256MiB（268,435,456バイト）** です。アップロード中も期限が進み、QRの表示時に期限を延長しません。サーバーが返す受取期限で残り時間を表示し、期限切れ時にQRを消します。受取完了・中止・期限切れで転送用コピーを削除します。PCから中止通知が届かなかった場合も、サービス側の期限による削除が適用されます。無料枠を保護する受付・日次転送量の上限があるため、混雑や上限到達時は新しい転送を受け付けません。時間を置くか、通常のファイル書き出しを利用してください。

クラウドの保存先に障害がある場合は、受取アクセスを停止したまま削除を再試行します。PCの保存完了表示はスマホへの正式保存を示し、クラウドの削除完了を確認した表示ではありません。

QRには受取用の認証情報と復号鍵が含まれます。QRを持つ人はアバターを受け取り、復号できます。共有、画面の撮影、ログや不具合報告への添付はしないでください。アップロード権限の認証情報はQRに含みません。

## 操作（開発環境）

1. **VR Vlog → lilToon VRM 1.0を書き出す** を開き、アバター・作者名・書き出し設定を指定します。
2. **スマホに送る** を押します。通常のExporterで完成したVRMを転送用の一時ファイルに保存し、転送画面を開きます。書き出し失敗時は既存の対策画面で修正します。
3. 一時保存の説明を確認し、**アップロードしてQRを表示** を押します。PCで暗号化してから転送を作成します。進捗を確認し、アップロード完了後にQRが出るまで待ちます。
4. スマホのVR Vlogで **モデルを変更 → PCから受け取る** を開き、アプリ内のカメラでQRを読み取ります。カメラの許可が必要です。
5. ファイル名と容量を確認して受け取ります。スマホは暗号文の認証を確認してから復号し、元の容量・SHA-256を検証して既存のVRM保存・読み込みへ進みます。鍵が違う場合やファイル・QRのメタデータが改ざんされた場合は採用しません。
6. PCに保存完了が表示されることを確認します。状態は5秒ごとに確認するため、スマホでの完了から表示まで少し時間がかかります。

完了・中止・期限切れ・失敗後は **新しいQRを作成** で、同じ完成済みVRMから転送を作り直せます。以前のQRは再利用できません。画面を閉じるとPCの転送用一時VRMも削除します。その後に新しく転送する場合は、再度 **スマホに送る** で書き出してください。通常の **保存先を選んでVRMを書き出す** で保存したVRMはこの後始末の対象になりません。

## 接続できないとき

| 状況 | 対処 |
| --- | --- |
| アップロード失敗／受付上限 | インターネット接続を確認し、新しいQRを作成する。混雑時は時間を置く。通常のVRMファイル書き出しも利用できる。 |
| QRが読み取れない | VR Vlog内のカメラを使い、QR v3対応のアプリか確認する。古いLAN QR・QR v2は利用できない。 |
| 期限切れ／転送中止 | PCで新しいQRを作成する。PC・スマホの日時も正しく設定する。 |
| スマホ保存完了、PCの状態確認に失敗 | アバターを再受信する必要はない。PCの接続を確認するか転送画面を閉じる。残っている転送用コピーも受取期限で削除される。 |
| 容量やSHA-256が一致しない | 受信ファイルを採用せず、新しい転送を作成する。 |
| 転送画面を閉じた／Unityを再読み込みした | 待機中の転送を中止し、PCの転送用一時ファイルを削除する。必要なら改めて書き出す。 |

## 検証の範囲

開発時のホスト試験では、独立Python生成の共通ベクトルと実際のC#ストリーム暗号化を比較し、合成データとfake transportで暗号文のmultipart分割、復号した元ファイルとの一致、HTTPへの鍵・元のメタデータの非送信、再発行時の鍵・IV更新、公開完了前のQR非表示、中止の競合、期限切れ、一時ファイルの後始末を検査します。既存LANは無効のままで、旧プロトコルのTLS loopback回帰も継続します。

暗号化プロファイルは [RFC 7518 A256CBC-HS512](https://www.rfc-editor.org/rfc/rfc7518.html#section-5.2.5) です。PCは標準のAES-256-CBC/PKCS7とHMAC-SHA-512を使い、元の名前・容量・SHA-256を認証対象に含めます。サービスは暗号文の容量・ハッシュ、通信元、時刻、転送状態を扱います。E2E暗号化はPCやスマホ自体、QRを撮影・共有した場合のアクセスを保護するものではありません。

クラウドサービスへの実アップロード、配布パッケージとAndroid・iPhone配布版の一連の転送、対応Unity 2022.3 Editorのコンパイル・画面・テストは別途確認が必要です。ホスト試験や別Unity版の参照DLLコンパイルを、これらの実機確認として扱いません。
